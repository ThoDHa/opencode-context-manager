# opencode-context-manager architecture

## Abstract

opencode-context-manager is an [opencode](https://opencode.ai) plugin that manages context windows with least-recently-used eviction. Chat APIs are stateless: every request re-sends the conversation so far, so a session's input bill grows quadratically in its length while its content grows linearly. The plugin maintains the history per turn under a chosen watermark: zero-loss dedup and expiry passes run every turn; eviction runs last, only above the watermark, against candidates ordered by recency, and replaces evicted outputs with tombstones that a `recall` tool restores verbatim from a persistent page store; ingestion hygiene strips terminal escape noise once, at birth; a metrics log, a session checkpoint, a `describe` tool, and two TUI views make every figure observable. Above the watermark the transform pins per-request input near the watermark, converting quadratic growth toward linear. The accounting is approximate by design, the reclamation is bounded by exemptions, and the design's largest unquantified risk is the prompt-cache trade. Several mechanisms are adopted, with credit, from Tony Mason's openly developed agent-memory family (fsgeek on GitHub).

## 1. Introduction

Chat APIs are stateless: every request re-sends the conversation so far, so per-request input grows monotonically and a session of N turns bills about c times N squared over 2 input tokens for content that grew only linearly (derived in [The token economics](#7-the-token-economics)).

This plugin maintains per turn under a chosen watermark, tiers by information value (zero-loss dedup and expiry every turn; eviction last, only above the watermark, against candidates ordered by recency), makes eviction reversible through the page stores and `recall`, is observable end to end (metrics log, session checkpoint, `describe`, the `/context` panel, the session sidebar), and keeps native auto compaction as the overflow backstop. Two admissions bound it: on sessions that never grow it is inert, and where a provider discounts cached prefixes heavily its trimming can forfeit more in lost cache hits than it recovers in bytes; it does not model cache state and does not claim to.

This document is the repository's architecture specification: it states the system model, the mechanisms, the economics, and the evidence. Evidence here means stated results, each carrying its corpus, observation window, and method inline ([Measured observations](#12-measured-observations)); the [README](../README.md) carries installation and the configuration reference.

## 2. Background and related work

opencode's config schema (https://opencode.ai/config.json) ships adjacent mechanisms: `tool_output.max_lines` and `tool_output.max_bytes` (defaults 2000 and 51200) truncate oversized tool output at ingestion, full text saved to disk and a preview returned, bounding what enters rather than what accumulates; `compaction.auto` (default true) fires, in the schema's words, "when context is full", with retention knobs (`tail_turns`, `preserve_recent_tokens`, `reserved`) and a manual on-demand form; `compaction.prune` (default false) clears old tool outputs into markers; per-model `cache_read` and `cache_write` pricing makes re-sent history cheaper rather than smaller. Each leaves the gap this plugin targets: compaction is reactive at the ceiling, one large lossy event whose summaries have no recovery path; the prune is positional, unaware of what the model still touches, its markers naming no subject, size, or way back; caching leaves the model attending over the full context with unknown quota effects.

The third-party plugin field (public descriptions and repository metadata as of 2026-09-18, the Sleev site as captured 2026-09-07) confirms the gap rather than filling it. DCP (`Opencode-DCP/opencode-dynamic-context-pruning`, about 4.2k stars, AGPL-3.0) is the strongest entry: a model-invoked `compress` tool replaces stale conversation spans with LLM-written summaries, and its deduplication and errored-input-purge strategies are adopted deliberately here as two of this plugin's passes; beyond that shared layer it fails every design commitment (model tokens spent per pass, the model deciding when and what to compress, the summary the only carrier of a replaced span with no reload path, recency gating a fixed turn window instead of refreshing on use), and its published measurement of the cache trade-off flagged below as this design's largest risk (roughly 85 percent hit rate with pruning against 90 without) is the cautionary number. Sleev, DCP's commercial successor proxying Claude Code, Codex, and OpenCode, shares the summary cost model and adds an infrastructure dependency every request routes through, where this design's problem is one opencode install kept deterministic and dependency-free. The observability projects (`IgorWarzocha/Opencode-Context-Analysis-Plugin`, about 180 stars, stale since 2025-10, no license, which alone bars code reuse; `ttalkkak-lab/opencode-contexty`, AGPL-3.0) analyze rather than trim, contexty's one trimming path being an embedded DCP configuration. `viiqswim/opencode-compaction-guard` repairs the native collapse's `tool_use without tool_result` failure, which this design's passes never cause; the better lever is shrinking how often the collapse fires. Upstream was asked for both halves of this design (issue #22407: pointer-based retrieval for compacted tool results; issue #32189: context-aware pruning) and closed both without maintainer engagement.

Claude Code, Anthropic's agent harness for the same model family, ships this job natively. Its documentation describes the progression directly: as context fills, Claude Code "clears older tool outputs first, then summarizes the conversation if needed"; auto-compaction summarizes history as the session approaches the auto-compact window, `/compact` is the on-demand form (focus instructions inline, or a "Compact Instructions" section in CLAUDE.md), and `/context` shows what is consuming space. Around the trimmers sit prompt caching managed automatically, MCP tool definitions deferred until tool search loads them, subagents working in their own context windows, and `/clear` between unrelated tasks. The plugin cannot run there anyway: it hooks opencode's message transform, a surface Claude Code does not have.

The honest nuance is that the native mechanisms are lossy too: the documentation describes no recovery for cleared tool outputs, removed images must be re-shared, compaction keeps a structured summary in place of the verbatim history, and compaction invalidates the prompt cache by design, the same trade flagged below as this design's largest unquantified risk. The page stores, `recall`, and touch-based ordering are absent there, and fine to leave absent because the native stack covers the need by default; this plugin exists for the harness whose maintenance of accumulated history stops at a reactive collapse and a default-off prune.

Two industry surveys anchor the surrounding claims with public sources. First, a survey of shipped coding-agent harnesses (vendor documentation fetched 2026-09-27 and 2026-09-28: Claude Code, Codex CLI, Gemini CLI, Cursor, Cline, aider, opencode) found summarization-based compaction the uniformly shipped answer to context growth, always at the cost of one extra model call at compaction time and composed with prompt caching for the input side; published price tables across the same vendors put cached input at 0.1 to 0.25 times the uncached price, which is exactly the discount that turns any history mutation into a measurable cache trade. The measured alternatives never shipped: the LLMLingua prompt-compression family reports 2x to 20x compression with small-model scoring (EMNLP 2023 through ACL 2024, arXiv:2310.05736, arXiv:2310.06839, arXiv:2403.12968) but appears in no shipped harness, and translating prompts into a denser natural language measures as an inversion on Western tokenizers (the same document cost between 7.8 and 182.4 percent more tokens in Chinese across six tokenizers in an April 2026 test, with lower task success; arXiv:2604.14210 and the six-tokenizer study at markhuang.ai/blog/chinese-token-myth), so no production translation pipeline exists. This design sits deliberately outside both families: it spends no model calls, and what it removes is either fully redundant, already converted into visible output, or restored verbatim on demand.

One host behavior deserves its own statement because the install layout is built around it, verified by reading the host source at v1.18.33: opencode assembles plugin origins by concatenating config-file tuples first and per-directory scan results after, then keeps the last origin per file, so a file the scan can discover (sitting directly inside a config-dir directory named `plugin` or `plugins`; the scan is a one-level glob of `.ts` and `.js` files across the global config dir, every project `.opencode/` directory up the tree, and `~/.opencode`) silently displaces the tuple that configures it, and the tuple's options are dropped with no error on either side. A registered entry therefore must not be scan-discoverable: the recommended clone directory name (`opencode-context-manager`) and the developer symlink directory (`context-manager`) both exist to stay outside that scan. The TUI runtime reads plugins only from `tui.json`'s `plugin` array and never scans directories, which is why the TUI entry lives in its own config file.

## 3. Inspiration and credit

The design's mechanism vocabulary was not invented in a vacuum: it adapts, with attribution, patterns from a family of openly developed agent-memory projects maintained by Tony Mason under the GitHub account fsgeek (https://github.com/fsgeek). A survey of the account's public repositories (September and October 2026: profile enumeration, per-repository sources, and a release-window review) found nine interoperating, Quechua-named projects attacking different tiers of the same problem this plugin attacks, plus a deep systems-research back catalog. The projects are credited by their public repositories, and each adoption below names the mechanism it shaped here; the bullets credit six of the nine, and the remaining three (yanantin, tiksi, and pukara, the epistemic-primitives trio) round out the nine while contributing vocabulary rather than mechanisms to this design.

- **qhaway** (https://github.com/fsgeek/qhaway), a budgeted memory index with declared omissions, is the family's seed and the deepest contributor. qhaway itself is in live use as an MCP memory server in this plugin's development environment, so its semantics are exercised daily rather than admired from afar, including its `supersedes` and `retracts` revision semantics and its event log's delivery stamping. Four mechanisms here are qhaway's directly: the declared-omissions footer (the `omissions` block of `describe` and the standing-omissions footer appended to native compaction), the counts-only cost probe (`recall`'s `countsOnly` mode prices a reload without loading content), version-stamped lines with a per-process session id (`pluginVersion` and `pluginSession` on every metrics line), and refuse-to-downgrade store versioning (the page store's `schemaVersion` stamp and the append halt on first sight of a newer version, adapted from a qhaway fix whose rule is that an older tool version must never destroy a newer tool version's store).
- **tinkuy** (https://github.com/fsgeek/tinkuy), "virtual memory for transformer context windows", contributes three mechanisms: the advisory pressure band below the watermark (from its pressure zones: surface the approaching threshold and the candidates it would consume, while actual removal still fires only at the threshold), the fault penalty in the eviction sort (a recorded fault defers a candidate five messages in the ordering, from its fault-count scoring where recalled content resists re-eviction), and the persistent page store of verbatim evicted originals (from its PageStore, written eagerly at eviction).
- **tampu** (https://github.com/fsgeek/tampu) contributes honest absence: a `recall` miss declares its scope instead of implying emptiness (only pages evicted during this session are stored, and no prior-session page matched either), and the page store's occupancy and capacity are reported through `describe` and the checkpoint rather than hidden.
- **khipumaq** (https://github.com/fsgeek/khipumaq) contributes the plain staleness sentence: the `/context` panel ages the newest transform and the newest metrics write in words ("last transform N minutes ago"), its pattern of saying plainly when ingestion looks stale instead of leaving the reader to diff raw timestamps.
- **AssFS** (https://github.com/fsgeek/AssFS) contributes reason-tagged retention: the retention audit names, per held entry, the reason it is held (`inWindow`, `retainedRead`, `protectedTool`, `patternProtected`, `faultShielded`), making retention auditable rather than implicit, in the spirit of every hold recording why it exists.
- **hamut'ay** (https://github.com/fsgeek/hamutay) contributes the research framing the whole design rests on: the context window is a cache, not a memory, and models never volunteer a record of what they discarded, so discard honesty has to be designed in. The tombstone-and-reload loop, the metrics log, and the declared omissions are that principle made mechanical.

The adoptions are stretched to fit a plugin runtime, and the family's remaining ideas are deliberate non-adoptions for that reason: no proxy gateway architecture (tinkuy runs a proxy; this plugin is in-process with transform hooks and needs none), no model-cooperative compression (the family's tensors need a plugin-callable model API that opencode does not expose), no database-backed stores (qhaway's index and khipumaq's episode store carry infrastructure this runtime deliberately lacks), no HTTP observability surface (pichay's endpoints duplicate what the metrics log, `describe`, and the two TUI views already serve in-process), and no telemetry of model internals (pacmi26-observability's gameability argument validates the metrics log conceptually but its state-object telemetry is unreachable from a plugin). qhaway's `supersedes` and `retracts` semantics stay on the memory-server side of the boundary: verbatim session pages rarely supersede one another.

Acknowledgments: Tony Mason (fsgeek) designed and built the family this design borrows from, and this plugin's debt to that work is explicit and structural.

## 4. Method (system model)

The Context Manager is the plugin at `plugin/context-manager.ts`, with the TUI panel and sidebar in `plugin/context-manager.tui.tsx`, their shared data layer in `plugin/panel-data.ts`, and the shared totals schema both data sides consume in `plugin/schema.ts`. It hooks the transform opencode runs on the message list before every model call and trims what the provider is about to receive. Loaded through the install's `opencode.json` entry, the core plugin runs in every session opencode opens, a subagent's included. The surface is three hooks and two tools: `chat.params` captures the session's context limit when the model is chosen, `experimental.chat.messages.transform` rewrites the outgoing message list on every turn, and `experimental.chat.system.transform` delivers a one-line hint into the system prompt; `recall` reloads evicted content from the page store, and `describe` reports the live counters as JSON. The `/context` TUI panel (the `context.panel` command, registered by the TUI file) and the same file's persistent session-sidebar entry are read-only views over the plugin's metrics log and the per-session checkpoint ([Observability](#6-observability)). The repository's test suite (`make test` over the nine files under `tests/`) pins the mechanism claims; the comparisons, the economics, and the observed sessions below are argument and measurement, not test outputs.

### 4.1 The transform pipeline

One transform run executes, in order: a hint strip removes stale `[ctx-hot]` text parts left in the message list; tool-output dedup replaces an older identical call's output with a `[ctx-deduped]` tombstone pointing at the newer copy; file-attachment dedup replaces an older duplicate `file` part with a text tombstone naming the newest occurrence; the errored-input purge replaces a failed call's recorded input with `[ctx-purged-input]`, keeping the error output; reasoning expiry deletes `reasoning` parts outright once they sit strictly older than the retention age; fence eviction (default off) replaces an over-threshold fenced code block in an old user message with `[ctx-evicted-fence]`; and watermark eviction replaces the coldest completed tool outputs with `[ctx-evicted]` tombstones until the estimate falls under the watermark. The README's [What this plugin does](../README.md#what-this-plugin-does) section carries the same stages as a one-glance table with each stage's firing condition. After the passes, the run counts faults (post-eviction re-references of evicted subjects), records counters, stores the hint line for the next system-prompt build, appends one metrics-log line when the run did anything at all, and rewrites the session's checkpoint.

### 4.2 Token accounting and the context limit

Token accounting is approximate by design: text parts and completed tool outputs are sized in characters divided by the `charsPerToken` factor (four by default), carrying tokenizer error without needing a tokenizer. The context limit resolves in a fixed order: a `modelContextTokens` entry keyed `providerID/modelID`, then the model's declared context limit from `chat.params` (accepted only when finite and positive), then an explicit `defaultContextTokens`, then nothing; unknown means eviction stands down rather than inventing a limit, while dedup, purge, expiry, fence eviction, and the hint still run and native auto-compaction remains the overflow backstop. One option-to-field mapping names the rest of this document's figures: the README option tables' context limit ([Context limit and eviction](../README.md#context-limit-and-eviction), the `modelContextTokens` and `defaultContextTokens` resolution) is reported by `describe` as `contextLimit` with its `contextLimitSource`, the metrics line and checkpoint persist under the same `contextLimit` names, and the sidebar renders the figure as `Context limit`. The watermark is half the context limit (the `watermark` ratio defaults to 0.5 and must lie strictly between 0 and 1), `recentWindow` defaults to 4 messages, reasoning retention to the same boundary, `minEvictableBytes` to 2048.

### 4.3 The options channel

The install layout follows from the host behavior [Background](#2-background-and-related-work) verified: a configured entry's options reach the plugin only while the entry's file is not scan-discoverable, and the drop-on-invalid discipline means a value failing validation is discarded with the documented default applying, so a mistyped option degrades to default behavior instead of blocking a session. One consequence is worth naming: `charsPerToken` accepts any finite number above zero, so extreme-but-valid values are not rejected either; a tenth or a ten-thousand-fold factor is accepted and the token estimate degrades gracefully with it (eviction starts implausibly early or late while the zero-loss passes and the context-limit resolution stay correct).

## 5. Mechanisms

### 5.1 The no-loss passes

Tool-output dedup scans the message list newest first. A call's identity is the tool name plus a key-order-insensitive serialization of its input, so two calls differing only in JSON key order dedup; an older identical call's output becomes a `[ctx-deduped]` tombstone naming the message holding the retained copy, with the superseded copy's `state.attachments` stripped. The tombstone forms only when the retained copy itself clears the 2048-byte floor, the pass has no recent-window guard and needs no context limit (a duplicate is redundant wherever it sits), and marker-prefixed outputs are skipped on every later pass, so repeated transforms are idempotent. File-attachment dedup runs beside it: a `file` part (the `@`-reference surface, carrying `mime`, `url`, an optional `filename`) whose `mime` and `url` both match a newer occurrence becomes a text tombstone naming it; identity is content (identical basenames in different directories never collapse), the newest occurrence is always retained verbatim, occurrences inside the recent window are never tombstoned, and no size floor applies because a `file` part's payload size is not observable from its `url`. Range-read collapse runs beside both: read calls of the same path with an `offset` and `limit` (rendered `path:start-end` in subjects) fragment one file into standing windows dedup cannot see, every distinct window being a distinct key, so a read whose `[start, end)` range is fully contained in a strictly newer retained read of the same path becomes a `[ctx-deduped]` tombstone naming both its own window and the retained range and message. Containment only: a contained window provably adds no unique lines, while a merely overlapping or merely contiguous window may carry lines the retained window lacks, so those stay (contiguous full-file chunk reads are therefore not collapsed automatically). The discipline mirrors dedup: reads inside the recent window never collapse, outputs under `minEvictableBytes` never collapse, and already-tombstoned outputs never collapse or resurrect; each collapsed window's output bytes count once into `collapsedWindowBytes` (the estimate `collapsedWindowTokensSaved` divides them by `charsPerToken`), and `collapsedWindows` counts the tombstones, both flowing through the metrics line, checkpoint, `describe`, and the panel like the dedup totals.

The errored-input purge keeps a failed call's error output (often the only record of what went wrong) but replaces its recorded input, which can be large, with `[ctx-purged-input]` once the call ages out of the recent window. Reasoning expiry deletes `reasoning` parts strictly older than the retention age, wagering that reasoning from earlier turns has no consumers: the producing model already converted it into visible output. The age is `reasoningRetentionMessages` when set and the `recentWindow` boundary when unset, and one signature property is guaranteed by construction only at the window edge: the signature-carrying thinking block an immediately pending tool-use continuation needs always sits inside the `recentWindow`, and the clamp keeps that block inside the retained span for any option value, but a delegation loop longer than the window loses the blocks of its earlier steps at the default setting, which is precisely what a widened retention (12 to 16 for delegation-heavy sessions) buys back within its measured per-request cost: the option is documented under [Context limit and eviction](../README.md#context-limit-and-eviction), and [Measured observations](#12-measured-observations) carries the study behind the range. Expiry is plain deletion with nothing stored and no reload path; it runs whether or not a context limit is known and is counted separately from evictions (distinct parts and first-crossing bytes on `describe` and in the metrics log), never added back.

### 5.2 Watermark eviction

Every completed tool output of at least `minEvictableBytes` that is not already a tombstone is an evictable candidate, with subjects extracted: file paths (with `offset`/`limit` ranges when present), grep and glob `pattern` strings, bash command strings. A candidate's `lastTouch` starts at its own message index and refreshes forward on any later call against the same subject: exact match for paths, substring containment for bash commands whose length exceeds `minSubstringMatchChars` (three by default), ranged and whole-path calls refreshing each other. Exemptions: outputs last touched inside the recent window, the `task` and `todowrite` tools (the `protectedTools` default, overridable), subjects matched by the `protectedPatterns` glob list (a bash command's path is the command, so the same globs guard commands), outputs under the floor, and anything already tombstoned.

Candidates sort coldest first by last touch adjusted for faults (ascending `lastTouch` plus `faultCount * FAULT_PENALTY_MESSAGES`, ties by descending size; each recorded fault (a `recall` reload of the subject or a post-eviction touch re-referencing it, one fault per event) adds five messages of deferral), so recalled content resists re-eviction under equal pressure while a large enough deficit still evicts it; above the watermark the plugin computes the token deficit and walks the list until the reclaim covers it, so a one-token overshoot evicts exactly one output, and only the evicted output's own bytes earn credit (tombstone and digest bytes stay in context), so `bytesReclaimed` never overstates what left. A tombstone reads, in one line: `[ctx-evicted] <tool> <subject> (<bytes> bytes[, attachments dropped], ~<age> messages ago) was evicted to reclaim context; re-run the tool to reload its output. Output digest: <digest>. Evicted output stored in the page store; recall it with recall (subject "<subject>").` The subject caps at 160 characters. The digest is deterministic string work, so identical content always yields an identical digest: `read` outputs contribute the subject plus previews of the first and last lines, `bash` outputs the command plus head and tail lines, every other tool a bounded excerpt of the output head; newlines collapse and the whole digest caps at 200 characters. Attachments leave with the output: the evicted part loses its `state.attachments` array entirely and the tombstone gains the `attachments dropped` clause.

### 5.3 The session page store and recall

Eviction does not destroy: each evicted output becomes a page in the session page store, the per-session in-memory map holding 50 (`stashLimit`) entries per session with the oldest dropped, 8 (`stashSessions`) sessions retained with the least recently active session evicted first. `recall` returns the stored original named by subject, passed exactly as the tombstone names it: the newest match in full, one-line pointers to any older matches; a subject with no page anywhere returns a miss message stating that only pages evicted during this session are stored and that no prior-session page matched either. A hit refreshes the session's store against the 8-session bound; a miss probe and a `describe` call do not, so idle sessions' stores age out first. Fence evictions share the same store and bound. Reload cannot re-serve binary attachments (the tool returns a string, and re-serving megabyte data URIs would re-inflate the context eviction just reclaimed): it appends a manifest naming each attachment's mime and data-URI length and advises re-running the original tool to regenerate them.

The store also persists: every stored eviction lands as one JSONL line in the page store ([Observability](#6-observability) documents the store's format and versioning), so `recall` keeps working across restarts and across sessions. When the session page store has no match, the tool consults the page store and returns the newest page in full, marked as restored from the page store, with a count (not an enumeration) of any older pages and the attachments manifest when the page carries one; a page hit counts as a recall and records the fault on the subject, so reloaded content resists re-eviction in the reading session, with one parity limit: unlike a session-page-store hit it does not refresh the reading session's store recency against the 8-session bound. The session page store keeps precedence, and its responses stay byte-identical to the single-session behavior.

`recall` also prices a reload without paying for it: called with `countsOnly: true` alongside the subject, the tool walks the same session-store then page-store lookups a full reload walks and returns one counts line instead of any content, naming the in-session match count, the page-store match count, the newest match's byte size, the older-match count, and an attachments-present flag. The probe is side-effect-free by construction: it returns before the recall-hit increment and the fault record on the hit path, and before the miss increment on the miss path, so `recallHits`, `recallMisses`, and the fault counts that feed the eviction sort key stay untouched (a probe can never make a subject resist eviction), it does not refresh the session store's recency, and a probe miss returns exactly the standard miss text. Omitting `countsOnly` or passing `false` gives the full-content responses byte for byte.

### 5.4 User-fence eviction

Fence eviction is the one pass that edits user prose, so it ships default-off behind `userFenceEviction` (`{ enabled: false, minBlockLines: 40 }` when unset). When enabled, it scans the text parts of user messages outside the recent window for fenced code blocks under CommonMark fence rules: an opener is at least three backticks after at most three spaces of indent (four or more spaces is indented code, never a fence, and an info string holding a backtick never opens a block), the closer needs at least as many backticks as the opener, an unterminated block is never touched, an all-blank block is never evicted since it names nothing. A closed block whose content spans strictly more than `minBlockLines` lines becomes an `[ctx-evicted-fence]` tombstone naming the language tag (the first word of the info string when present), the content line count, and the first non-empty content line as the reload subject; the prose before, between, and after the fences is preserved byte for byte, the exact removed span enters the session page store for verbatim `recall` restore, and the pass runs before the context-limit decision, so fence bytes lower the estimate and can spare tool outputs an eviction.

### 5.5 Compaction enrichment

When the host's native compaction fires (the SDK's `experimental.session.compacting` hook), the plugin appends context strings to the native compaction prompt so the summary it produces names what the session can still reload: a `[ctx-hot]` hint line in the same shape the system prompt carries (the session's remembered evicted subjects rendered newest first and bounded by `hintSubjects`), a one-line `[ctx]` note stating that tombstoned outputs remain reloadable via `recall` and naming the newest stored subjects when the session page store holds reloadable outputs, and a standing-omissions footer, `[ctx] standing omissions: <N> tool outputs, <M> reasoning blocks, <K> fenced blocks; reload via recall`, rendered whenever the newest run's declared omissions carry a non-zero category (the same figures the `omissions` block of `describe` reports). The hook appends only; it never sets the SDK's `prompt` field, so the host's default compaction prompt is never replaced. It stays silent for a session with no recorded evictions (an unknown session attaches nothing and creates no state), contributes the store note when a session page store holds entries but no subjects are remembered, and a `hintSubjects` of 0 silences the two subject-rendering lines entirely (0 disables subject rendering everywhere else) while the omissions footer still renders on a non-zero newest run, being a count line rather than a subject rendering. The body runs behind the same fault boundary as every other hook: a throw leaves the native prompt unmodified and records the failure as `lastError` on the session's diagnostics, so compaction proceeds without the enrichment.

### 5.6 Ingestion hygiene

Tool outputs are cleaned at birth rather than per request: the SDK's `tool.execute.after` hook rewrites a completed output before it reaches session storage, so the stripped version is what the session file keeps and what every later request sends, and the transform never re-pays the scan. Three passes run in order: CSI and OSC escape spans are removed (the same span pattern the composition walk counts for `escapeBytes`, with a non-greedy OSC payload so consecutive OSC hyperlink spans each end at their own terminator and the link text between them survives), carriage-return progress lines collapse to their final segment within each newline-delimited line (`10%\r20%\rdone` keeps only `done`, while a `\r` that closes a line as CRLF or sits at end of output is a line ending and is carried through untouched), and trailing runs of spaces and tabs are trimmed from each line with leading whitespace left alone. A rewrite happens only when it changes something: a clean output costs one scan and zero writes, and a byte-identical result passes through as the original string.

`ingestionHygiene` (default `true`; a non-boolean falls back to the default) turns the strip off entirely. `ingestionHygieneCopy` (default `true`) controls the disk-copy escape hatch: when a rewrite changes an output, the original lands as one JSONL line in `ingestionHygienePath` (default `~/.local/share/opencode/context-hygiene.jsonl`) before the rewrite is applied, carrying the tool name, the title when available, the original and stripped lengths, and the full original output, mirroring the host's own full-text-to-disk discipline for the paranoid case. `ingestionHygieneRotationMaxBytes` (default 5 MiB, `0` disables the copy but not the strip) rotates the file to a `.1` sibling before an append that would exceed the cap, the same two-generation scheme as the metrics log. The title, metadata, and any attachments are never touched, only the output text.

Degradation is explicit in both directions: a failed copy write surfaces as `hygieneWriteError` through `describe` and the stripped rewrite still lands, while any other throw in the hook leaves the tool result with its original text and records `lastError` on the session's diagnostics, so a hygiene bug can never block or corrupt a tool result.

## 6. Observability

After each run the plugin stores a `[ctx-hot] recently active: ...` line naming up to ten (`hintSubjects`) most recently touched live subjects, newest first; the system-prompt hook appends it or replaces the previous one in place, making the working set visible so tombstones stay navigable.

The metrics log is on by default and appends to `~/.local/share/opencode/context-metrics.jsonl` (`metricsPath` relocates it). Every eventful run appends one JSON line; eventful means at least one eviction, dedup tombstone, expired reasoning part, fence eviction, or fault, or any recall since the previous line, so quiet runs write nothing. A reasoning-only eventful run (expiry is the only eventfulness) inside `metricsMinLineIntervalMs` (default 60000, `0` disables coalescing) of the session's previous line writes nothing instead, because expiry re-reports the session's standing aged set every run and those re-reports carry no new information between lines; the window is measured from the session's previous flushed line and a suppressed run does not move it, so sustained reasoning-only traffic settles at one line per interval, and any eviction, dedup, fault, fence event, or recall flushes immediately regardless of the window, as does a change in the context-limit source against the last flushed line. The interval bookkeeping is per-process memory: a restart forgets it and the next eventful run writes, so coalescing never loses the first line of a sitting. Under coalescing, a line count therefore means eventful flushes rather than eventful runs (the panel's `runs` figure and the log-tail rehydration seed inherit this; the checkpoint still covers quiet runs and stays run-faithful), a degree change, not a kind change: the count already excluded quiet runs and now also folds coalesced reasoning-only runs into their nearest preceding or following flush. Each line carries a timestamp, the session id, the plugin's version and per-process session id under `pluginVersion` and `pluginSession` (the version is the `PLUGIN_VERSION` constant in `plugin/schema.ts`, bumped as a release step; the session id is drawn once per plugin process, so the same host session logs under a new id after an opencode restart and every line of one sitting shares it), the context limit with its source (`override`, `model`, `default`, or `unknown`, under the `contextLimit`/`contextLimitSource`/`contextLimitModelKey` fields; resolved from a live `chat.params` capture, the explicit `defaultContextTokens` option, or the limit persisted with the session's newest record in the checkpoint or the metrics log tail, whichever is fresher; the persisted value is suppressed, and eviction stands down, when the session has since changed models or when the config no longer carries the override entry or default option the persisted limit came from), the estimate against watermark and deficit, per-entry eviction records (tool, subject, bytes, attachment bytes, age in messages), dedup, expiry, fence, and fault counts, recalls since the previous line, and running totals that cover the session's lifetime and are restored across process restarts from the session's checkpoint or log tail: the raw counters, the unique-event counts (`dedupedUnique` first tombstones per content-identical duplicate pair, `reasoningExpiredUnique` content-identical reasoning parts counted the first run each crosses the retention age), the first-crossing superseded-duplicate byte total (`dedupedBytesUnique`), and the four token-savings estimates (`evictionTokensSaved`, `dedupTokensSaved`, `collapsedWindowTokensSaved`, `reasoningTokensSaved`). `bytesReclaimed` counts evicted output and attachment data-URI characters plus fence-block bytes, and dedup records each pair's superseded byte size once at the pair's first tombstone (a superseded `file` part records none, since its payload size is not observable from its `url`); expiry bytes go to `reasoningBytesExpiredUnique`, purged inputs count nowhere. Each line also carries the composition of the request after every pass has run: `toolPoolBytes` (live tool-output bytes, tombstones included; dedup and eviction tombstones remain tool outputs), `textChars` (user/assistant text characters, range-collapse and file-dedup tombstones included), `reasoningInWindowBytes` (reasoning bytes still inside the retention age; the key predates the retention knob and kept its name and its parser contract, but with `reasoningRetentionMessages` set it counts the widened retained set rather than only the recent window), `escapeBytes` (terminal escape sequence bytes inside live tool outputs, the candidate an ingestion-side ANSI strip would reclaim), and `attachmentBytes` (live attachment payload bytes: tool-state attachment url payloads and file-part url lengths, the same surfaces eviction's attachment accounting covers; embedded images inside file parts, data-URI text outputs, and non-attachment host content are not counted). Over the same post-transform list the identity is exact: `estimatedTokens` equals ceil((`toolPoolBytes` + `textChars`) / `charsPerToken`); `reasoningInWindowBytes` and `attachmentBytes` are not components of the estimate (the estimate counts text plus completed tool outputs only), and neither is the system prompt or other host extras; those are bill components the estimate omits, which is why the logged figure is a floor. `describe` reports the same figures for the session's newest run in a `composition` block. `reasoningInWindowBytes` is the observable that sizes the retention knob: it is exactly the per-request byte bill a widened `reasoningRetentionMessages` adds, so sizing the knob against the watermark is arithmetic over it rather than a guess, and `attachmentBytes` makes the image-expiry candidate arithmetic instead of a guess; `escapeBytes` sizes the strip candidate the same way.

The count and savings semantics agree by construction, and reading either as a per-request figure misstates the session: the dedup and reasoning counts are unique-event lifetime figures, identified by content, so a duplicate pair counts when its tombstone is first created and a reasoning part when it first crosses the retention age, and identical-content occurrences count once in count and bytes alike; the reasoning byte total (`reasoningBytesExpiredUnique`) credits each part's length at that same first crossing, `dedupedBytesUnique` credits each duplicate pair's superseded output and attachment bytes once at that pair's first tombstone (when one run supersedes several copies of the same pair, the first-admitted pair, the newest superseded copy, is the one whose bytes credit, while the `deduped` count still rises once per tombstone), and the token estimates divide those first-crossing byte totals by the resolved `charsPerToken` factor, not billed-token measurements: eviction divides its reclaimed bytes, dedup divides each pair's superseded bytes counted once, and reasoning expiry divides the first-crossing bytes. That is why the sidebar renders, say, `Reasoning expired: 321, 53.2M tokens`: the count is distinct parts and the savings is the estimate over their first-crossing bytes, one coherent statement of distinct work rather than a per-request re-filtering multiplied by request count. The unique counts and bytes are per-entry lifetime figures: their seen-content memory lives on the session's entry in the metrics store (entries evict least recently active past the `metricsSessions` bound), so an entry evicted and later reseeded re-counts and re-credits that session's standing set once per entry lifetime. The per-request cost of expiry remains observable where it belongs, on the line: `reasoningExpiredThisRun` and `reasoningBytesExpiredThisRun` carry the standing aged set each request filtered, and the reasoning-only coalescing behavior keys off that per-run figure unchanged. A widened `reasoningRetentionMessages` shrinks the standing aged set, so the first-crossing counter and byte total grow more slowly than under the default, a change in the crossing rate, not in the semantics. `metricsRotationMaxBytes` (default 20 MiB, `0` disables) renames the file to `<metricsPath>.1` before an append that would exceed the cap, so only the current and previous generations exist; a failed stat, rename, or append surfaces as `logWriteError` through `describe` without interrupting the session. The two-generation cap bounds how much history survives: anything older than the current and previous generations has rotated out permanently, and [Measured observations](#12-measured-observations) (Observation 4) carries the rotation-rate arithmetic behind these windows, including how line coalescing changes the rate. A fault, a later call re-referencing an evicted subject (a `recall` reload or a post-eviction touch), is the feedback signal that makes eviction's error rate measurable rather than assumed.

The session checkpoint is the second data source for both TUI views, on by default (`liveStateLog` turns it on or off; `liveStatePath` relocates its directory, `~/.local/share/opencode/context-state/`). Every transform run with a last-run record rewrites `<session id>.json` there: a timestamp, the session id, manual mode, the resolved context limit with its source under the `contextLimit` field names (persisted with an optional model identity in `contextLimitModelKey`, in the checkpoint and each metrics line, so a restart resumes the session's context limit instead of flickering it to unknown; a live `chat.params` capture always wins over the persisted value, a change of model or the removal of the config override or default the persisted limit came from suppresses it so eviction stands down rather than refilling a stale limit, and an absent or null pair in an old record rehydrates to unknown, the pre-persistence behavior), the last run against watermark and deficit, the session's lifetime running totals (restored across restarts), the session page store's occupancy and capacity under `pageStore`, and the hot subjects. The write is atomic (a sibling temp file renamed into place, never a torn read), a failure surfaces as `stateWriteError` through `describe`, and files older than `liveStatePruneMaxAgeMs` (default seven days, `0` disables pruning) are removed on a directory scan throttled to one per `liveStatePruneMinIntervalMs` (default 60 seconds, `0` disables the throttle). Because the checkpoint covers quiet runs, live state exists even when the log is silent.

The newest run's retention audit rides the same checkpoint and `describe`: a `retention` block naming the live tool-output pool size (scanned before the run's own evictions, so a run's pool includes the entries that run then evicted) and, per reason, how many pool entries each protection holds. The five reasons are the eviction machinery's own words: `inWindow` (born inside the recent window), `retainedRead` (born before it but re-touched back in), `protectedTool`, `patternProtected`, and `faultShielded` (a recorded fault shifted the entry's sort key; the block reports the largest shift in messages the faults bought). Reasons are counted independently, so one entry held by several mechanisms counts under each and the sum reads as diagnostic, never as a total: the block answers why nothing is being evicted, not how many entries there are, and the fault shift is what classification time saw, not a survival guarantee (pressure still evicts a faulted entry); faults credited during the run reach the fault counts before the audit but after that run's sort keys were computed, so in the crediting run the reported shift is what the next run's sort buys. A run that scanned no live tool outputs writes no retention block at all, and the `/context` panel renders the matching `retention:` row (pool, the five counts, and the fault shift) between the counters row and the newest-eviction row only when the newest run carried a pool.

The page store makes stored pages survive restarts and session boundaries: on by default (`pageStore`; `pageStorePath` relocates the file, default `~/.local/share/opencode/context-pages.jsonl` beside the metrics log), every stored eviction appends one JSONL line in the same transform run that built it, carrying a timestamp, the session id, the tool, the subject, the message and part indices, the fence span slot when a fence eviction wrote the line, and the full verbatim output plus the attachment descriptors when the eviction dropped any. `pageStoreRotationMaxBytes` (default 20 MiB, `0` disables writes) rotates the file to a `.1` sibling before an append that would exceed the cap, the same two-generation scheme as the metrics log, so the record is bounded to two generations; a failed write surfaces as `pageStoreWriteError` through `describe` and never blocks the eviction. Every line names its own `schemaVersion` (currently `1`), stamped at write time so a store shared across plugin versions classifies line by line: an unstamped line (everything earlier builds wrote) reads as the current version, and a line whose finite version is strictly newer is skipped uninterpreted. The first observation of a newer-version line, on the `recall` walk or on a walk run immediately before a rotation rename, permanently halts that plugin instance's appends and rotation (the older build can then neither bury the newer store's pages into the `.1` generation nor append behind them), and the observing session's `describe`, and the `describe` of any session that evicts under the halt, carries a `pageStoreSchemaError` diagnostic explaining the stoppage; known-version pages keep serving through `recall` meanwhile, and a garbage version value on an otherwise-valid line stays corruption (skipped like any malformed line, no halt). The read side is the cross-session `recall` path [the session page store and recall](#53-the-session-page-store-and-recall) documents: the store is consulted only after the session page store misses, the newest matching page returns in full, older pages count without being enumerated, and a corrupt or unreadable store degrades to a clean miss (malformed lines are skipped individually, and any failure never throws into the tool).

Privacy: the store is where the plugin writes tool output content verbatim for the long term, so the posture is explicit. The content serves only the `recall` reload path; read subjects reach no new log, panel, sidebar, or checkpoint surface; rotation bounds how long any line survives; and `pageStore: false` removes the record entirely, writing nothing and reading nothing. The content class is not new to disk: the host's own session storage already persists every pristine tool output verbatim, indefinitely, for the same machine and user, and the hygiene copy writes full originals beside the metrics log; the store adds an explicit rotation bound and a one-switch opt-out on top of that baseline. Set `pageStore: false` when the machine is shared and the host's own persistence is not acceptable either.

The metrics totals schema is declared once, in `plugin/schema.ts`: the producer's counter seeding and totals emission and the panel parser's required-key checks all derive from the same key list, so a counter addition is one edit instead of a six-file lockstep. The panel's log reader tolerates lines the strict parser rejects, whatever the reason (totals missing a schema key, malformed evicted entries, a missing or mistyped field): a session carrying such a line contributes only its newest parseable line (only sessions carrying rejected lines collapse; sessions whose every line parses strict keep their full run history and eviction footer), so the global block degrades gracefully across schema growth instead of blanking until old lines rotate out; the strict parser itself is unchanged, and a session whose every log line is rejected shows no log-derived data (a checkpoint, when one exists, still serves that session's block) until its next run writes a current record. Strictness has one transitional pair and one reset list. The transitional pair: `processedContextBytes` and `processedContextTokens` postdate the other raw counters, so an absent processed-context key in a persisted record is read as `0` rather than rejected (mirroring the producer's own seeding tolerance for the same gap) while every other missing or non-finite key still rejects the record. The reset list: the five keys the 2026-10-02 rename touched (`recallHits`, `recallMisses`, `pagesDropped`, `faults`, `dedupedBytesUnique`) plus `reasoningBytesExpiredUnique` sit on the required list, so a totals block missing any of them predates that boundary (the reasoning key the first-crossing totals reset, the renamed ones the vocabulary reset) and both the producer's seeder and the strict parser reject the record outright, resetting that session's persisted totals to zero until the next eventful run writes a current one; the old lines keep their per-run fields readable in the raw log, so per-request history is not lost. [Migration and reset semantics](#11-migration-and-reset-semantics) carries both accounts in full.

`describe` returns an echo of the resolved options (a fixed subset covering the context-limit, logging, mode, and boundary settings plus the estimate factor `charsPerToken`, the remembered-evicted-subjects bound `rememberedEvictedSubjects`, and the `protectedTools` and `protectedPatterns` exemption lists, not the full [Configuration](../README.md#configuration) surface), the effective context limit with its source and its `headroomTokens` (the limit minus the newest run's estimate, null when the limit is unknown or no run exists), the session page store's occupancy and capacity under `pageStore`, every counter, the last run's estimate, watermark, and deficit, and, after any run has landed on the session, an `omissions` block carrying the newest run's declared omissions by category (`toolEvictions`, `reasoningParts`, `fenceBlocks`, derived from the same run outcome the counters accumulate) plus the `reloadTool` pointer naming `recall`, so the model can read the shape of what the last run left out and price reloading any of it before spending the tokens; it stays the full-detail surface. The echoed boundary figures are the resolved ones, not the configured ones: `recentWindow` as floored and `reasoningRetentionMessages` after its clamp (a configured value below `recentWindow` echoes as the window it clamps up to, and an unset one echoes as the window default). The rows the two views no longer spend stay reachable elsewhere: session id, session page store occupancy, and the recall hit, miss, and drop counters through `describe`, hot subjects through the hint line and the session checkpoint, and the unfiltered run history only in the metrics log itself. Each view reads the log anew at open or poll, filters to the session it serves, and prefers the session checkpoint for the session block: a session log line newer than the checkpoint wins the fields it carries, and a missing or malformed checkpoint falls back to the log. What renders differs by view: both read the same two data sources, and each draws from its own row builder in `plugin/panel-data.ts`, so the exact text of both is unit-tested without a terminal. The `/context` dialog renders `panelRows`, the compact form: a header row (`Context Manager`, suffixed `(manual)` only in manual mode), the context limit with its source, the last run against the watermark with the deficit, an advisory row when the newest run carries an advisory preview, between the last-run row and the counters row (the pressure band [Staged engagement](#8-staged-engagement) documents), one compact counters line (evictions with reclaimed bytes and its token-savings estimate, dedup count with its estimate, recalls with hit count), and, once the metrics log carries an eviction for the session, the newest one as a single info-toned line naming tool, subject, size, and age, plus a final staleness sentence aging the two timestamps the data layer already carries (`last transform <age>` against the session checkpoint's `ts`, `metrics last written <age>` against the newest session log line's `ts`, ages reading `just now` under a minute and whole minutes, hours, and days beyond; the transform clause drops for a log-fallback session with no checkpoint, and the whole row drops when neither timestamp resolves). The sidebar renders `sidebarRows`, spaced for its narrow column (about 42 characters) as three blank-line-separated groups: the header, one stat block, and, once the metrics log carries an eviction for the session, the newest one as an info-toned two-line footer naming tool, subject, size, and age. The stat block lines read `Context limit: <compact tokens>`, `Watermark: <compact tokens>`, `Over by: <compact deficit>` (present only when the last run's deficit is non-null and above zero), `Window: <compact tokens>` (the newest run's estimate of the live context window, the same figure the panel's last-run row shows; the row renders whenever the session block itself renders because a block exists only after a completed run, and it is the plugin's own estimate, so it sits below the host Context block's figure by design: the estimate counts post-transform text plus tool outputs and omits reasoning retained in window, the system prompt, tool schemas, and host-injected sections), `Advisory: <ratio> of watermark (<compact band start> tokens), <compact estimate> est, <pressure>` (present only when the newest run's estimate sits inside the pressure band, the same advisory preview the panel's advisory row shows, truncated to the column limit), `Tokens processed: <compact> tokens` (the session's own cumulative token spend: the running sum over every request of that request's processed context at the bytes/4 estimate, so it grows with each request and is neither a current-window figure nor provider-billed usage; the same estimate the subagents group's token rows show), `Evictions: <count>, <savings estimate> tokens`, `Deduped: <count>, <savings estimate> tokens`, `Reasoning expired: <count>, <savings estimate> tokens`, and `Recalls: <count>, <hits> hits`; a null context limit renders as `Context limit: inactive (no context limit)` and a missing watermark as `Watermark: none`, and the sidebar carries no context-limit source label (the panel keeps its label). The block carries the hierarchy in the theme's own tones: the context limit, watermark, and window rows render in the normal text tone, the over-by row and the advisory row in the warning tone, and the five counter rows in the success tone; the header row keeps the header tone, the eviction footer the info tone.

With `sidebarSubagents` enabled the sidebar appends one last blank-line-separated group for the session's subagent children (sessions carrying this one as their parent, fetched through the TUI API each tick): every non-archived child is within scope regardless of how old its last update is or whether it is still running, and archived ones never render. A normal-toned lead row `Subagents: <count>` opens the group with the agent-name label treatment (info-toned bold label, plain value) so the count anchors the group visually, and it ships as one visual unit with what follows it: whenever any child's data has landed, the cumulative block renders directly beneath with no blank row between, opening with the normal-toned row `Tokens processed: <compact> tokens` (the total token usage across all subagents), then the four stat rows in the type blocks' exact shapes, every figure summed over all landed children across types; the block renders nothing when no child's data has landed; a blank row always precedes each type block, so with the cumulative block rendered the blank separates the block's last row from the first type row, and without it the lead row from the first type row, and every type block still separates from the next by one blank. Each type block opens with a normal-toned row carrying an info-toned bold agent name with a plain-text count, `Explore: 2 agents` for a multi-child type and `Explore: 1 agent` for a single-child one; each landed type adds five normal-toned rows beneath its type row, leading with `Tokens processed: <compact> tokens` (the token usage summed over the type's landed children), then `Evictions: <count>, <compact tokens> tokens`, `Deduped: <count>, <compact tokens> tokens`, `Reasoning expired: <count>, <compact tokens> tokens`, and `Recalls: <reads>, <hits> hits` (reads are hits plus misses), every figure summed over the type's children whose data landed and the rows mirroring the session stat block's own counter rows; a type whose children have no recorded data yet renders `<type>: no data yet`, type rows hold a fixed order regardless of activity recency, the four fleet agent types first in the sequence worker, verifier, reviewer, planner (matched case-insensitively), then every other type in code-unit order by its type string, and every row truncates with an ellipsis against the sidebar's column limit. The token figures are the plugin's own estimate, `ceil(bytes / charsPerToken)` over the processed context each child session's transforms carried (post-transform tool outputs plus text); provider-billed usage is unreachable from the plugin and is not what these rows show. The group degrades silently: a tick whose children fetch fails or that finds no non-archived children renders the sidebar exactly as with the option off.

The sidebar entry registers through the TUI plugin API's `sidebar_content` slot when `sidebarEnabled` is true (the default; a non-boolean value falls back to true, and `false` skips only that slot registration while the `/context` command stays registered; the same registration reads `sidebarSubagents`, default false, which adds nothing on its own while the slot itself is off) and re-renders on a five-second poll of the same two files, visible only while the session has recorded data: a tick whose log read fails with no checkpoint to fall back on hides it for that tick (startup and log rotation produce such transient failures), and the next poll repaints. The poll's timer and its post-await writes are dispose-guarded, so a route change or plugin shutdown cannot write through a disposed component.

The `sidebarMode` TUI option narrows what the sidebar area shows: `full` (the default) leaves the host's built-in sidebar content plugins in place, while `context` deactivates the four built-in plugins contributing to the same `sidebar_content` slot (`internal:sidebar-mcp`, `internal:sidebar-lsp`, `internal:sidebar-todo`, and `internal:sidebar-files`) through the TUI API's `plugins.deactivate` at every load, leaving what the session-name slot renders, the host's own Context block (`internal:sidebar-context`, deliberately kept active), and the Context Manager block; the footer plugin lives in the separate `sidebar_footer` slot and is never touched. The deactivations ride the sidebar registration, so with `sidebarEnabled` false, or on a host build without the slots registry, `context` mode deactivates nothing and the sidebar area is whatever the host renders without the plugin's entry. Deactivation re-applies on every TUI load with no persistence assumed, an unrecognized value falls back to `full`, and a host build without a callable `plugins.deactivate` (or whose deactivate calls fail per plugin) skips those deactivations silently, rendering the full sidebar. The plugin's own sidebar entry renders identically in both modes.

Degradation is explicit and identical in both builders: "no active session" outside a session, "no metrics recorded for this session yet" for a session with no runs, malformed lines skipped at parse, and an unreadable log leaving the checkpoint-fed session block under a warning row when a checkpoint serves the session, header and warning row alone otherwise.

## 7. The token economics

Suppose a session adds roughly c tokens of new content per turn. Request n then carries about n times c input tokens, and a session of N turns bills about c times N squared over 2 input tokens in total: quadratic in session length, for content that grew only linearly. The overhead multiple is about N over 2: a 60-turn session bills roughly thirty times the content's worth, almost all of it settled history the model will not touch again.

The passes form three tiers of increasing aggression, each with an explicit information trade. Tier zero removes dead weight at no loss: reasoning expiry and the errored-input purge delete content whose consumers are gone (expired reasoning was already converted into the visible output that replaced it; a purged failed-call input sits beside the error text that matters), firing every turn regardless of the context limit, which is why a long session's metrics show most reclamation happening before any eviction. The no-loss claim for expiry is the consumer claim, not a permanence claim: `reasoningRetentionMessages` widens how long the bytes stay before expiry takes them, trading the guaranteed-zero-loss framing for kept reasoning whose bill the `reasoningInWindowBytes` composition field makes visible. Tier one removes pure redundancy at no loss: a dedup tombstone only replaces an output fully duplicated by the retained newest copy, and the floor keeps trivial outputs from erasing substantial ones. Tier two trades old tool outputs for small references above the watermark: the tombstone answers "was this file read, and what did its first line say" without a reload but does not substitute for the content; the original reloads verbatim from the page store (binary attachments the exception), and the recent window, the protected tools (`task` outputs carry a subagent session's report, `todowrite` outputs carry plan state, both expensive to reconstruct), and the pattern exemptions bound what may leave.

In aggregate: under the watermark only the no-loss tiers apply and per-request cost still grows with history; above it, eviction pins per-request input near the watermark (each run trims just far enough to fall back under), and cumulative input falls from quadratic in N toward linear in N. That conversion, on top of the zero-loss tiers, is the entire economic argument.

What engages when: the zero-loss passes fire on pattern presence alone (a reasoning part aging past the retention age, an identical call repeating, a failed call aging out); no context limit is needed. Context-limit-driven eviction needs an effective watermark and an evictable candidate outside the exemptions; missing any one yields zero watermark-tier evictions by design (the aged read tier of [Staged engagement](#8-staged-engagement) is the deliberate exception: armed, it evicts without a context limit). The effective watermark is `watermarkTokens` when set (an absolute token figure) and the captured context limit times `watermark` otherwise, so `watermarkTokens` also lets eviction engage on sessions whose limit was never captured. `describe` distinguishes the stand-downs: an unknown limit leaves `contextLimit` itself null, and the `manualMode` option (default false, a non-boolean value falls back to false) suspends context-limit-driven eviction while dedup, purge, expiry, fence eviction, the hint, the page stores, and both tools keep running. A manual run records the effective watermark and the deficit against it whenever one exists (a captured limit or a set `watermarkTokens`), the same figures the dry run acts on, so the sidebar and `describe` show the real numbers while nothing evicts; a manual run with no effective watermark nulls the last run's watermark and deficit, and the sidebar renders `Watermark: none` for it. The shape this produces on real workloads is documented twice over: a delegation-heavy long session expiring hundreds of reasoning parts with zero evictions ([Measured observations](#12-measured-observations) carries the figure with its corpus), where every turn delegating to a subagent leaves a reasoning block and the blocks age out of the four-message window long before the watermark engages; and its complement, the short-lived session, a handful of turns, nothing past the recent window, often no logged line at all.

## 8. Staged engagement

The fractional watermark of a 1M-context model is 500k tokens, and observed sessions peak near 275k ([Measured observations](#12-measured-observations)), so the default has never engaged even while those sessions billed tens of millions of input tokens a day. `watermarkTokens` is the first staged lever: set it to 250000 and only sessions crossing a quarter million engage, leaving everything smaller untouched; it wins over the fractional watermark when both are configured, and the same finite-above-zero drop-on-invalid discipline applies.

The intended flow is evaluate-then-engage: set `manualMode` plus `watermarkTokens` together, run for days, and watch the dry run. In manual mode with an absolute watermark set, every run computes what the evictor would reclaim (the deficit against the watermark, and the candidate set walked in the same coldest-first order with the same exemptions the real evictor uses, stopping at the deficit for non-aged candidates: an armed aged read tier keeps the walk going for its own candidates) without mutating anything. `describe` carries it as a `dryRun` block (deficitTokens, wouldEvictCount, wouldEvictBytes, wouldEvictSubjects truncated to the `rememberedEvictedSubjects` bound) for the newest run of the session, and the metrics line carries `wouldEvictThisRun` and `wouldEvictBytesThisRun` whenever the dry run is active (zeros under the watermark, absent otherwise); both are run-scoped diagnostics, never persisted and never part of the totals schema. One accounting asymmetry to read correctly: `wouldEvictBytes` counts candidate output bytes only, while post-engage `bytesReclaimed` also adds attachment payload bytes, so engaged counters can legitimately exceed the dry-run prediction when candidates carry attachment payloads. When the evidence says the watermark is safe, turn `manualMode` off and the same watermark engages for real.

The advisory pressure band makes the approach visible before the watermark engages: when the newest run's pre-eviction estimate reaches `advisoryBandRatio` times the effective watermark (0.85 by default, so the band starts fifteen percent below the fire line), the run carries a preview naming the ratio, the band start, the estimate, the deficit against the watermark, and the first three candidates the evictor would schedule, read from the same ordered candidate walk eviction itself uses. `describe` renders it as an `advisory` block beside the dry run, the `/context` panel renders it as a row between the last-run row and the counters row, and the sidebar renders a truncated `Advisory` row after the Window row; the preview persists through the session checkpoint as an optional field pre-change snapshots simply lack, so the panel keeps showing it between transforms. The band is advisory only: eviction still fires at the effective watermark, which makes the watermark itself the critical zone and the band's ceiling, and a run above the watermark reports the deficit as already over. Composed with manual mode the advisory computes exactly as in automatic mode alongside the dry run, so the evaluate-then-engage flow shows both the projected reclamation and the approaching pressure. A session that never approaches the watermark stays silent, because the preview exists only in-band: the band is zero-risk foresight, not an activity meter.

The aged read tier (`agedReadEvictionMessages`) is the second staged lever, and it ships default-off. Where the watermark tier handles limit pressure, the aged tier handles staleness: when set, read-family outputs whose birth position sits older than this many messages from the list tail are evicted through the same machinery as watermark-tier evictions (same tombstones with digests, same page stores, same counters), whatever the limit and watermark say, which is what engages the 100-200k mid-size sessions the watermark never touches. Read-family means the tools whose subjects the touch tracker refreshes by exact path equality: every path- or pattern-subject tool except the bash command channel, whose outputs the tier excludes (re-running a command is an action rather than a re-read, and the corpus's re-request evidence is read-shaped: models re-request by issuing new range reads, which is precisely the tombstone's advertised recovery path, and the read-marathon session's zero-percent input repeat across 67 runs ([Measured observations](#12-measured-observations)) is the bound on the re-injection risk for the observed workload). Two protections carry over untouched: a re-touched subject never ages out (a read of the same path inside the recent window refreshes its touch and shields it, however ancient the original message), and the recent window, protected tools, protected patterns, and `minEvictableBytes` all still apply. Both tiers can be armed together and share one walk: the aged tier evicts its entries whatever the limit says, the watermark tier covers the remaining deficit, and each candidate takes exactly one disposition, so neither tier double-counts. The staging flow is the same evaluate-then-engage: set `manualMode` plus `agedReadEvictionMessages`, and the dry run's `wouldEvict` figures report the combined watermark and aged policy, so days of dry-run lines measure exactly what enabling would do before `manualMode` goes off. One precondition names itself: the dry run only runs when an effective watermark exists, so staging on sessions whose limit was never captured means setting `watermarkTokens` too.

The safety argument for that flow is verified against the host source, not inferred: `experimental.chat.messages.transform` output is a per-request view. opencode reloads the message list fresh from SQLite at every chat-loop step, hands that request-scoped list to the hook, and sends the result to the provider only; no storage write path ever receives the transformed list, so eviction edits the outgoing request and re-runs against stored originals on the next request, meaning it cannot destroy stored data, and the tombstone's reload pointer stays durable even after a restart orphans the in-memory session page store. The verification method: the host's session-loop source was read at each named release and at a current dev build, comparing the message-list data flow (reload from storage per chat-loop step, plugin trigger on the request-scoped list, provider send, discard; no write-back anywhere in the pipeline), with no drift in the relevant control flow across ten months of releases and two runtime architectures (only the named releases and the dev build were read; the intermediate releases were not bisected). Confirmed at opencode 1.1.4, 1.18.5, and 1.18.32 plus current dev (host `prompt.ts`: message list reloaded from storage per step, plugin trigger, provider send, discard).

## 9. Reliability

Every hook and tool body runs behind a boundary so a plugin bug degrades instead of surfacing as a raw error in the host. A throw inside the transform hook returns the message list either untouched (a fault before the body starts editing) or with the partially applied normal edits it had managed (the same message references, a subset of the healthy edits, never a corrupted structure), and records the failure on the session's diagnostics, where `describe` surfaces it as `lastError` (the error message plus a timestamp; run-scoped, never persisted, replaced by the next fault). The `chat.params` handler degrades to no-op on a throw, keeping whatever context-limit state the session already had. A throwing tool call returns a `[ctx-error] <message>` string the TUI can render instead of throwing. The system-prompt hook returns the prompt unchanged when its hint delivery fails. On the TUI side, `api.slots.register` and `api.keymap.registerLayer` are each reached only after a guarded property check confirms the host api object actually carries the callable registry they need (a hostile getter counts as absent); a host without them loads the plugin with the core transform and both tools working, and no views or panel command registered.

## 10. Honest limits

What it cannot reduce: input history only. Output tokens (the model's answers), the per-request fixed payload (system prompt and tool definitions, plus the plugin's one hint line), and the number of requests are all invisible to it, and a session's cost floor is fixed overhead times request count.

Approximate accounting: characters over four is a proxy with tokenizer error in both directions, so eviction can start somewhat early or late; attachment payload characters count toward `bytesReclaimed` but not toward the estimate; tombstone and digest bytes add back weight the reclaim credit ignores. The log's numbers are directional, not billing-grade.

Reclamation is bounded by exemptions: the recent window, protected tools and patterns, the size floor, and already-tombstoned outputs all stay no matter the deficit. When the deficit exceeds what candidates can cover, eviction empties its list and stops short of the watermark: a context dominated by protected or sub-floor content cannot be trimmed to size.

The caching unknown: a prefix cache invalidates at the first changed message, every pass here mutates history, and eviction's coldest-first ordering targets the oldest messages, which is the deepest prefix. If the cached price sits far below the uncached one, both the dedup and eviction savings shrink, and aggressive trimming can forfeit more in lost cache hits than it recovers in bytes; the plugin sees no billing data and models no cache state. This is the design's largest unquantified risk.

Volatile state: the session page store lives in the plugin's memory for the server process, but its contents persist beside it: with the page store on (the default), a restart or a fresh session reloads stored originals through `recall` from the page store, so the no-page miss text now answers only when the subject was never stored anywhere or the store is off. The counters are not lost either: the session's first transform or `recall` hit after a restart rehydrates them from the session's checkpoint, or the newest metrics-log line for the session when no checkpoint serves it (a miss cannot initiate hydration, it only awaits one already in flight; `describe` alone neither creates nor rehydrates), so totals keep running across restarts. The remaining bounds: pre-reset records are rejected wholesale by the [reset boundary](#11-migration-and-reset-semantics) rather than partially seeded, a session with no surviving checkpoint (`liveStateLog` off) whose log line has rotated out of the current generation restarts its counters, and two processes resuming the same session each seed from the same base and count independently on top of it. A restart whose checkpoint and line writes both failed resumes from the last record that did land. The metrics log survives restarts but keeps only the current and previous rotation generation, and the page store the same two generations, so an original can still become unreloadable: its page rotated out permanently (bounded by `pageStoreRotationMaxBytes`), or the store was disabled. The 51st (`stashLimit`) eviction in one run drops the oldest page from the session page store, but the page store keeps serving that dropped page, since trim-dropped pages persist exactly like every other stored eviction; only the rotation bound above, the store being off, or a page written before the store existed take a subject unrecoverable.

Second order under plan caps: where usage is capped at the plan level and dominated by fixed per-request overhead times request count, trimming the variable history share of long sessions is a second-order lever. The plugin earns its keep as cheap insurance for the sessions that do grow long (an extended session coordinating subagents, a long interactive run): one plugin, four source files, default-on, doing nothing at all to sessions that stay small. It is not a rate-limit fix; the first-order levers, fewer requests and shorter fixed payloads, live outside it.

## 11. Migration and reset semantics

Updating from the previous `lru-*` data names is self-migrating: the plugin's first load with a default path configuration renames `~/.local/share/opencode/lru-metrics.jsonl` to `context-metrics.jsonl` (the rotated `.1` sibling moves with it), the `lru-state` snapshot directory to `context-state`, and `lru-hygiene.jsonl` to `context-hygiene.jsonl` (with its `.1` sibling), so the accumulated counters, session checkpoints, and hygiene copies survive the rename intact and keep seeding rehydration and the `/context` panel exactly as before. The move runs in the plugin's init before any hook or panel read, each rename targets its new name only while that name does not exist yet, and a current-name file already in place wins with the legacy file left readable beside it, so nothing already in use is ever overwritten or deleted; the rotated `.1` sibling carries this check of its own, so a load that renamed a primary but failed on its sibling moves the stranded sibling on the next load. A failed rename degrades safely: the legacy file stays where it is, the session proceeds, and the next load retries, because the condition simply re-runs each time the plugin starts. Migration runs only for the kinds the plugin has enabled (`metricsLog`, `liveStateLog`, and `ingestionHygieneCopy` respectively): a disabled kind's file is never read or written again and stays in place under its old name. A configured `metricsPath`, `liveStatePath`, or `ingestionHygienePath` is never touched, since the migration only serves the default locations. Session history that predates the rename keeps working: the previous `[lru-*]` markers (`[lru-evicted]`, `[lru-deduped]`, `[lru-hot]`, `[lru-purged-input]`) remain recognized wherever the plugin scans stored output, while only new emissions carry the `[ctx-*]` markers.

The 2026-10-02 vocabulary reset is the one non-migrating boundary: the persisted counter keys renamed (`stashHits` to `recallHits`, `stashMisses` to `recallMisses`, `stashDropped` to `pagesDropped`, `postEvictionTouches` to `faults`, `dedupedBytes` to `dedupedBytesUnique`), and every renamed key sits on the seeder's required list, so a record written before the reset is rejected wholesale rather than half-understood. The consequence, stated plainly: every totals family restarts at zero once per affected session, not only the five renamed counters, because the old record seeds nothing after the rejection; a session whose stored history is entirely pre-reset renders no metrics-log rows and no session-checkpoint block until its next eventful run writes a current record (the panel and sidebar go dark for that session in the meantime and recover on its next run); and the persisted context limit also stops rehydrating from pre-reset records, so the limit reads inactive until the next `chat.params` capture refills it. Pre-reset tombstone prose names a tool that no longer exists: stored sessions evicted before the reset carry `read_evicted` in their tombstones, and that name is not registered (accepted breakage, and the reason the rename shipped without an alias: a kept alias would have pinned the old vocabulary to the new counters forever, the exact mixing the reset exists to avoid).

## 12. Measured observations

All results in this appendix are observations from the plugin's own operational data on a single-user, delegation-heavy development workload (the plugin coordinates subagents daily, so its sessions are long, tool-heavy, and reasoning-rich). They are observations, not benchmarks: one workload, one model mix, one machine, no controlled comparison. Each entry states its corpus, observation window, and method inline.

**Observation 1: reasoning expiry is coextensive with eventfulness, and widened retention is affordable at the median.** Corpus: the plugin's metrics log, both rotation generations, 12,408 JSONL lines across 276 distinct sessions, zero parse failures. Window: 2026-09-22 through 2026-09-30 (8.2 days). Method: exhaustive per-line parse of both generations, per-session aggregation of first logged lines, and a standing-set cost model (each session's newest line's aged-set bytes) priced per request at the bytes-over-four estimate against the 250k-token watermark in use. Results: every eventful line in the window carries reasoning expiry (dedup rides on 37.5 percent of current-generation lines and 6.4 percent of the older generation), all 276 sessions already carry a standing aged set on their first logged line, and widening `reasoningRetentionMessages` to ages 12 and 16 costs a median of about 4.1k and 5.6k tokens per request (p90 about 10.9k and 15.8k), which is why ages 12 to 16 are the documented recommendation for delegation-heavy sessions; the unbounded alternative (retaining to the user-turn boundary) has a p90 of 13 to 18 percent of the watermark and a worst observed standing set worth about 114k tokens per request.

**Observation 2: the default watermark never engaged on the observed workload.** Corpus: the plugin's per-session checkpoint directory, 468 session snapshots read exhaustively (each carries the session's final estimate). Window: 2026-09-19 through 2026-09-26. Method: census of final-state estimates across all snapshots, plus full-lifecycle reads of the largest sessions' metrics lines. Results: 26 sessions (5.6 percent) ended at or above 100k estimated tokens, exactly 5 at or above 150k, and the observed peak is 275,440 against the 500k fractional watermark of a 1M-context model; the largest session's line rate over one day implies an estimated 27 million input tokens billed in that day (the plugin's own bytes-over-four estimate), all of it pre-eviction input the watermark never touched.

**Observation 3: a 954-part standing aged set.** Corpus: one long delegation-heavy session's final metrics line, recorded under the retired per-request-recounted counters (the totals semantics changed to first-crossing counting afterward). Window: a single final line at that session's last run. Method: direct read of the line's expired-reasoning fields. Result: 954 expired reasoning parts totaling about 3.18 MB, a standing aged set re-filtered and re-reported on every request rather than that much distinct work, with zero evictions and the estimate near 52k against a 500k-token watermark; under the current first-crossing semantics the same work credits 954 distinct parts and their bytes once each.

**Observation 4: rotation-rate arithmetic.** Corpus: the metrics log before line coalescing shipped. Window: 2026-09-22T01:45Z through 2026-09-26T12:52Z (4.47 days), 10,027 lines averaging 646 bytes. Method: line counts and byte sizes over the window reduced to a daily rate, applied to the rotation caps. Result: about 1.45 MB/day, so a 5 MiB rotation generation holds about 3.5 days (about 7 days across the two-generation pair, and 2.6 days had already rotated out permanently at observation time), while the shipped 20 MiB cap holds about 14 days per generation, roughly four weeks across the pair; line coalescing cuts the post-coalescing rate by an estimated 70 to 85 percent, extending every window proportionally.

**Observation 5: the read-marathon session.** Corpus: one session's complete metrics-line lifecycle. Window: 21 minutes on 2026-09-23 (17:40 to 18:01), 67 transform runs. Method: full-lifecycle read of the session's lines in the log. Result: the estimate climbed from about 12k to 275,440 tokens (+3,900 per run) with zero repeated tool inputs across all 67 runs and zero evictions; a watermark anywhere in the 150k to 250k range would have engaged mid-session, and the zero-percent input-repeat rate is the observed bound on the re-injection risk of evicting read outputs on this workload (models that need a file again issue a new range read of the same path, which is precisely the tombstone's advertised recovery path).
